打开一封邮件的原始内容（Raw Source），经常能看到这样的东西：

```
Subject: =?UTF-8?B?5L2g5aW977yM5LiW55WM55qE6KGo5Y2V?=
```

完全看不懂。

展开之后可能是"你好，世界的邮件"之类的。这就是 **MIME 编码**在起作用。

---

## 为什么需要 MIME？

最早的邮件协议（RFC 822）只能传纯英文文本——7 位 ASCII。不能带附件、不能发中文、不能发图片。

这明显不够用。于是有了 **MIME（Multipurpose Internet Mail Extensions）**，一个扩展标准，给邮件（后来也给 HTTP）加了三样东西：

1. **标识数据类型**——这段内容到底是纯文本、HTML、还是图片？
2. **编码二进制数据**——把图片之类的 8 位二进制数据转成 7 位 ASCII，塞进邮件里
3. **处理非 ASCII 字符**——让中文、日文也能在标题和正文里正确显示

MIME 很成功——现在 HTTP 的 `Content-Type` 也是从它来的。

---

## 两个核心头部

一个 MIME 消息里有几个关键头部：

### Content-Type

告诉接收方这段数据是什么类型。格式是 `类型/子类型`：

| 类型 | 例子 | 说明 |
|------|------|------|
| `text/plain` | 纯文本 | 最简单的文本 |
| `text/html` | HTML 文档 | 带格式的邮件正文 |
| `image/jpeg` | JPEG 图片 | 附件或内嵌图片 |
| `application/octet-stream` | 通用二进制流 | 不知道具体类型的附件 |
| `multipart/mixed` | 混合内容 | 同时有正文和附件时用 |

你能在网页的 HTTP 响应头里看到同样的东西——`Content-Type: text/html; charset=utf-8`，这就是 MIME 定义的格式。

## Base64

把二进制数据转成可打印的 ASCII 字符。

原理很简单：每 3 个字节（24 位）拆成 4 组，每组 6 位。

但这里有个容易想岔的地方——**6 位的值不是直接当 ASCII 码输出**，而是作为**索引**，去一张固定的字符表里查对应的可打印字符。

这张表定义如下：

| 值范围 | 对应字符 | 说明 |
|--------|----------|------|
| 0-25 | `A-Z` | 大写字母 |
| 26-51 | `a-z` | 小写字母 |
| 52-61 | `0-9` | 数字 |
| 62 | `+` | 加号 |
| 63 | `/` | 斜杠 |

举个例子。假设分组后的 6 位值是 `000001`（十进制 1）。如果不查表直接输出，ASCII 码 1 对应的是 `SOH`（Start of Heading）——一个控制字符，根本不能安全传输。

但查表之后，索引 1 对应的是 `B`，一个标准的可打印字符。网上那些 Base64 解码器把你输的东西解码成 `B`，也是这个道理——不是巧合，是索引映射。

```
原始数据：  01000100 01100001 01111000
                        ↓
6 位分组：  010001 000110 000101 111000
  十进制：    17      6       5      56
                        ↓   查表
对应字符：    R      G      F      4
```

**为什么非要查表而不是直接输出？**因为早期邮件协议只保证 7 位 ASCII（0-127）能安全传输，而其中只有 32-126 号是可打印字符。0-31 和 127 是控制字符，传输过程中很容易被网关篡改或丢弃。Base64 通过查表，把所有数据强制映射到 `A-Z`、`a-z`、`0-9`、`+`、`/` 这 64 个绝对安全的字符上，无论原始数据是什么，输出都不会包含非打印字符。

末尾可能出现 `=` 号——它不是 6 位分组查表得来的，而是当原始数据字节数不是 3 的倍数时用来补位的填充符。

缺点：编码后体积增加约 33%。但胜在通用——图片、压缩包、任意二进制都能编。

### 命令行里用 Base64

```zsh
# 编码
echo "你好" | base64
5L2g5aW9Cg==

# 解码
echo "5L2g5aW9Cg==" | base64 -d
你好

# 给图片编码
base64 < photo.jpg > photo.txt

# 解码回图片
base64 -d < photo.txt > photo.jpg
```

## Quoted-Printable（QP）

专为"大部分是 ASCII，偶尔出现非 ASCII"的情况设计。

规则很简单：非 ASCII 字符的每个字节用 `=` 加两位十六进制表示。

```
"你好" 的 QP 编码：
=E4=BD=A0=E5=A5=BD
```

纯 ASCII 字符原样保留。所以如果一篇文章里只有几个中文词或特殊符号，QP 编码结果大部分可读，体积膨胀也很小——通常只有 10-20%。

QP 在邮件正文里很常见，尤其是包含少量中文或特殊符号的情况。

## 邮件标题的特殊编码

上面讲的两种编码用在邮件**正文**里。但邮件**标题**（Subject、From 等）里的非 ASCII 字符怎么处理？

标准定义了一套专门的格式：

```
=?charset?编码方式?经编码的文本?=
```

拆开看：

| 部分 | 含义 |
|------|------|
| `=?` | 开始标记 |
| `UTF-8` | 字符集 |
| `?` | 分隔符 |
| `B` | 编码方式（B = Base64，Q = QP） |
| `?...?=` | 经编码的文本，中间夹着 `?` |

所以开头那个例子：

```
Subject: =?UTF-8?B?5L2g5aW977yM5LiW55WM55qE6KGo5Y2V?=
```

- `UTF-8` —— 字符集是 UTF-8
- `B` —— 用了 Base64
- 解码后就是："你好，世界的邮件"

如果标题需要混用中英文，邮件客户端会拆成多段：

```
Subject: =?UTF-8?B?5L2g5aW9?= =?UTF-8?Q?=EF=BC=8Cworld?=
```

解码： "你好，world"

## 如何在命令行查看邮件原始内容

用 `curl` 看一封邮件的原始 MIME 头（需要能访问的 IMAP 邮件）：

```zsh
# 用 mail 命令查看原始邮件（macOS/Linux）
echo "h" | mail | head -20

# 更简单：大部分邮件客户端都有"Show Original"功能
# 直接把邮箱里一封邮件的 Raw Source 贴到文件里看
```

看原始邮件的好处很多——能发现垃圾邮件的伪造头、查出实际发送服务器、看到邮件的真实编码。

## MIME 与 HTTP 的关系

MIME 定义的那套 `Content-Type` 格式被 HTTP 直接拿过来用了。你在开发者工具里看到的：

```
Content-Type: application/json; charset=utf-8
Content-Type: image/webp
```

本质上就是 MIME 规范的遗产。

当你在终端下载文件时，很多东西也依赖 MIME 类型来判断应该怎么处理：

```zsh
# 看看文件的 MIME 类型
file -I photo.png
# photo.png: image/png; charset=binary

# 或者用 mimetype 命令
mimetype index.html
# index.html: text/html
```

---

## 小结

- **MIME** 是让邮件能发非 ASCII 文本和二进制的扩展标准
- **Content-Type** 标识数据类型，HTTP 直接复用了这套格式
- **Base64** 把任意二进制转成 ASCII，增加 33% 体积，适合附件和中文标题
- **Quoted-Printable** 适合少量非 ASCII 字符，大部分内容仍可读
- 邮件标题里的 `=?UTF-8?B?...?=` 是 MIME 编码，用 `base64 -d` 就能解开
- 在命令行里用 `base64` 编解码、用 `file -I` 看文件 MIME 类型，都很实用
