读到系列的这个位置，我们已经摸过不少命令了。从 `ls` 列出目录、`cat` 拼接文件、`grep` 过滤文本，到 `sort` 排序、`sed` 按脚本替换、`wc` 数行数字数，再到用 `|` 把这一串串起来。做这些事的时候，我们可能只是"学会了怎么用"，但很少停下来问一句：**为什么这些东西被设计成这样？**

这篇想做的事情，就是把我们到目前为止零散接触到的工具和技巧，放在一张更大的地图上看。不是教新命令，而是梳理这些命令背后的设计思想——通常被叫做 **Unix 哲学**。

---

## 它不是什么"哲学"

"Unix 哲学"听起来像某种高深的理论体系，像是在 MIT 的课上才讨论的东西。其实不是。

Eric S. Raymond 在《The Art of Unix Programming》第一章里说得坦诚：Unix 哲学不是一个自上而下的形式化设计方法，不是从理论计算机科学的某个高塔上递下来的。它是**自下而上**长出来的——出自 Ken Thompson 和 Dennis Ritchie 这些人在 1969 年到 1970 年代早期写代码时的直觉和实践。它像一门手艺的师徒传统，靠耳濡目染传递，而不是靠标准文档。

Brian Kernighan 和 Rob Pike 在 1984 年的《The UNIX Programming Environment》序言中说得更直接：

> Much of the power of the UNIX operating system comes from a style of program design that makes programs easy to use and, more important, easy to combine with other programs.

这本书的序言里还有一句话值得我们记住：**"Our goal in this book is to communicate the UNIX programming philosophy."** 也就是说，Unix 哲学不是什么高深莫测的东西，而是一套如何设计程序的编程原则。写这本书的人认为，理解这些原则比学会哪条具体命令更重要。

---

## DO-ONE-THING-WELL：小而专的原子命令

最广为人知的一条原则——或许也是整个 Unix 哲学中最核心的一条——出自 Doug McIlroy（管道（pipe）的发明者）的原话：

> Write programs that do one thing and do it well.

这条原则放在今天看，可能觉得很自然。但想想 1970 年代的主流操作系统——当时的命令往往是大而全的庞然巨物，一个命令功能多到可以独立成一个小型应用。McIlroy 说的是反着来的：**不要写大程序，写小程序，每个程序只做好一件事。**

回顾我们系列中用过的命令，几乎每一个都是这个原则的体现：

```zsh
ls          # 只做一件事：列出目录内容
cat         # 只做一件事：把文件内容拼起来输出
wc         # 只做一件事：数行/词/字符
sort        # 只做一件事：排序
grep        # 只做一件事：按模式匹配文本
head/tail   # 只做一件事：取文件开头或末尾若干行
```

每个命令的功能少到我们用一两句话就能说清楚它的全部能力。它们不附带交互式界面，不试图同时做"排序并生成图表并发送邮件"。但这种克制恰恰是力量的来源——因为简单，所以容易组合。

一个有意思的细节：McIlroy 的原话其实是四条，前面的引文只引了第一条。他的完整建议是：

1. 每个程序做好一件事。
2. 输出应该是另一个程序的输入，不要夹带无关信息，不要强求交互式输入。
3. 快速写出原型，不要怕扔破烂。
4. **用工具，不用人。**

第四条在今天的语境下尤其有趣——它几乎预言了自动化脚本的思想。

## 管道：把原子命令串起来

单有原子命令是不够的。如果桌面上散落着一堆螺丝刀、扳手、钳子但没有办法把它们配合起来用，那它们还是各自孤立的。Unix 的解决方案是管道（pipe）——由 Doug McIlroy 在 1964 年的一份内部备忘录中首先提出，1973 年由 Ken Thompson 实现在 Unix 中。

McIlroy 那份备忘录里的原话很妙：

> We should have some ways of coupling programs like garden hose — screw in another segment when it becomes necessary to massage data in another way.

把程序像花园水管一样接起来。需要改变数据处理方式时，拧上一段新管子就行。

这个比喻直白有力。在我们系列里，已经用过很多次管道的威力了：

```zsh
# 统计当前目录每种文件类型的数量
ls -l | grep "^-" | wc -l

# 找到某一个目录下最大的三个文件
du -sh * | sort -rh | head -3

# 从进程列表中过滤并排序
ps aux | grep python | sort -k3 -rn

# 组合 sed 替换再计数
cat access.log | sed 's/.*\[//;s/\].*//' | sort | uniq -c | sort -rn
```

注意看每一条命令链。每个环节做的事情都极其简单——`ls` 只管列目录，`grep` 只负责匹配，`wc` 只会计数。但是通过 `|` 连接起来，它们的组合能做一件单个命令做不到的事情。

这就是 **Rule of Composition**（组合原则）在实践中的样子：把模块化的小程序通过通用接口串联，让系统的功能随组合而增长，每一步增加的功能量恰好等于管道中新增的那一节。

## 文本是通用接口

McIlroy 的三句名言最后一句是：

> Write programs to handle text streams, because that is a universal interface.

为什么选择文本？因为**文本是人类和机器都能理解的格式**。一个人可以用 `cat` 查看任何程序的输出，能读、能改、能传给另一个程序。不需要专门的解析库，不需要版本兼容的序列化协议。

这也是为什么我们在系列里反复用到 `grep`、`sed`、`awk`、`sort`、`uniq`——它们都是文本过滤器。一个程序的输出是文本，另一个程序的输入也是文本，中间的管道不需要关心两边各自在做什么。只要文本格式一致，就能连接。

对比来看，同时代的 VMS 和更晚的 Windows 在很长一段时间里倾向于使用二进制格式或结构化 API 作为程序间通信的方式。两种做法各有取舍：二进制更紧凑，解析效率更高；文本可读性差一些（看 `ps aux` 的输出和看二进制的进程列表完全是两回事），但**调试的时候不需要专门的工具**。用不着什么 "process viewer debugger"，直接用 `cat` 和 `head` 就能看。

文本作为通用接口还有一个副产品：**脚本化变得极其自然**。因为一切都是文本流，shell 脚本不需要额外的序列化层——它直接操作文本。这在系列里大量出现过的重定向和管道例子中表现得再明显不过了。

## KISS：保持简单

KISS 是 "Keep It Simple, Stupid" 的缩写。这条原则在 Unix 世界中比在其他任何系统中都要贯彻得彻底。

具体到使用层面，它体现在几个地方。

**命令是静默的。** 绝大多数 Unix 命令在成功时不打印任何消息。

```zsh
cp file1 file2    # 成功了？没输出就是成功
rm file           # 删了？没消息就是好消息
```

这被称为 **Rule of Silence**（沉默原则）——ESR 在书中专门列了一条。当一个程序没有异常情况可说时，就不说话。这跟很多其他系统的习惯正好相反：有些工具习惯输出 "Operation completed successfully"（操作已完成）。问题是——让用户确认"成功了没有"这件事本身就是一种认知负担。如果真的成功了，什么都不说就是最干净的做法。

**命令的默认行为是最常用的行为。** `ls` 不加参数就是列出当前目录——最常做的事。`cat` 不加参数就是读标准输入。`sort` 没有参数就对整行做字典序排序。默认情况下做最符合直觉的事，这是 **Rule of Least Surprise**（最小惊讶原则）在命令行接口上的体现。

**配置用文本文件。** 很少有 Unix 程序要求用户在 GUI 中配置、然后把配置写进二进制注册表。从 shell 的 `.zshrc` 到 Vim 的 `.vimrc`，从 Git 的 `.gitconfig` 到 SSH 的 `config`，一切都公开地写在纯文本文件里。对应到系列里，我们配置过的 `.zshrc` 和别名就是用这个方式操作的——不需要专门的配置编辑器，用 `echo`、`cat`、`nano` 或者任何文本编辑器就能改。

这个"点文件（dotfile）文化"本身就是 Unix 哲学的一个生动例子：配置文件就是纯文本，纯文本就是通用的，通用就意味着可以用任何文本处理工具对付它们——甚至可以用 `grep` 来找配置，用 `sed` 来批量修改。

## 具体印证：从系列中的例子看到哲学

把我们学过的具体操作和 Unix 哲学原则一一对应起来，看看设计思想在多大程度上渗透进了日常使用的每一个角落：

| 操作 | 对应的原则 |
|------|-----------|
| `ls`、`cat`、`wc`、`sort` 各自独立 | DO-ONE-THING-WELL |
| `du -sh * \| sort -rh \| head -3` | 管道组合（Rule of Composition） |
| 输出文本流，不输出二进制格式 | 文本是通用接口 |
| `success` 命令无输出 | Rule of Silence |
| 用 `>` 和 `>>` 重定向到文件 | 文本流通用接口 |
| `*`、`?`、`[]` 通配符展开 | 壳（shell）自己做简单的展开，不交给每条命令 |
| `.zshrc`、`.gitconfig` 是纯文本 | 配置即文本 |
| `sed 's/foo/bar/g'` 批量改配置 | 文本作为数据，程序作为转换器 |
| `grep -r` 递归搜索 | 保持简单，一次只做一种过滤 |

## 反例与反思：不是每条原则都完美

前面这些读下来，可能给人一种"Unix 哲学是完美的，所有 Unix 命令都严格遵循这些原则"的错觉。这不准确。

首先，Unix 哲学本身不是一个完整一致的体系。ESR 在书中列出了 17 条规则，McIlroy 的归纳是 3 条，Pike 在《Notes on C Programming》里又给出了完全不同的 5 条。每套归纳都有自己的侧重，也有自己的盲区。

其次，一些广受欢迎的命令**违背了** Unix 哲学。最著名的例子是 `ps` ——它的输出格式在不同 Unix 变种（System V vs BSD）上完全不同。`ps aux`（BSD 风格）和 `ps -ef`（System V 风格）做同一件事，但接口和输出格式不兼容。Rule of Least Surprise 在这条命令上并未得到遵守。

还有一个更实际的挑战：**现代命令行工具越来越复杂。** `git` 就是一个典型例子——它有几十个子命令，每个子命令又有十几个选项。很难说 `git` 是一个"做一件事并做好"的工具。但它又是目前几乎所有人都在用的工具。这种复杂度暴露出"单一职责"原则在真实世界中的极限：当问题本身足够复杂时，工具也会跟着复杂起来。

另一个方面是图形界面对文本流的挑战。文本作为通用接口的优势在终端中无可辩驳，但到了 GUI 世界中就失去了立足之地。一个 GIMP 或 Figma 产生的 `.psd` 文件是二进制格式，没法通过管道把它串到另一个程序中。不同设计工具之间通过标准化的中间格式（如 SVG、PNG）交换数据，但这些格式不是为了方便管道组合而设计的——而是为了方便用户手动操作。**文本作为通用接口这一原则，在图形化软件生态中并未被继承。**

换言之，Unix 哲学是**在特定历史条件下解决特定问题的产物**。它在操作系统层面和文本处理领域表现极为出色，但把它当作放之四海皆准的绝对真理，就过于理想化了。

## 结语：为什么这些老观念还在用

Unix 哲学诞生于 1970 年代初期，距今已经半个多世纪。我们提到的那些书——《The UNIX Programming Environment》1984 年出版，《The Art of Unix Programming》2003 年出版——照计算机行业的更新速度，它们应该早就被淘汰了。但奇怪的是，这些书还在被阅读，这些原则还在被讨论，我们每天还在用着体现这些原则的命令。

原因也许很简单：**这些原则不是在解决上层应用的问题，而是在解决底层接口和系统设计的问题。** 上层应用的问题会随产业变化不断翻新，但接口设计上的基本权衡——模块化与否、通用还是专用、简单还是复杂——从来不会过时。每次我们在终端里敲出 `cat file | grep pattern | sort | uniq -c` 这样一行命令，相当于又一次验证了五十年前 McIlroy 在贝尔实验室提出的思路。

所以这篇不打算教什么新东西。它只是把我们学过的内容，用另一种视角再看一遍。工具还是那些工具，但当我们知道它们为什么那样设计之后，用起来的感觉会不一样——这就够了。
