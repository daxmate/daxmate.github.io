打开一个文本文件，看到一堆 `å\x9B\xBE\xE7\x89\x87` 或者 `���`——乱码了。

原因很简单：**文件存的时候用一种编码，打开的时候用另一种编码**。编码不对，文字就显示不对。

---

## 什么是编码

电脑不认识文字，只认识数字。**编码就是文字和数字之间的映射表**。

比如 `A` 在 ASCII 编码里对应 `65`：
- 存：把 `A` 转成 `65`
- 读：把 `65` 转成 `A`

中文的编码比较复杂——汉字太多了，一个字节（0-255）根本不够用。于是有了各种方案：

| 编码 | 特点 | 常用场景 |
|------|------|----------|
| **ASCII** | 7 位，只用前 128 个字符 | 英文文本 |
| **GBK / GB2312** | 中文编码，每个汉字 2 字节 | 老旧系统、Windows 中文版 |
| **UTF-8** | 可变长度（1-4 字节），兼容 ASCII | **现代通用标准** |
| **UTF-16** | 大部分字符 2 字节 | Windows 内部、Java |
| **ISO-8859-1** | 单字节，支持西欧字符 | 老旧欧洲文本 |

---

## 为什么会有 UTF-8

ASCII 设计于 1960 年代，当时只需要处理英文，7 位（0-127）就够用了。第 8 位留作奇偶校验，不是编码的一部分。

后来电脑进入欧洲市场，发现不够用了——ä、é、ü 这些带重音的字符没地方放。于是把闲置的第 8 位利用起来，扩展到 **0-255（1 字节）**。128-255 这一段各家定义不同——西欧用 `ISO-8859-1`（也叫 Latin-1），东欧用 `ISO-8859-2`，俄语用 `KOI8-R`。这就是最早的一批**扩展 ASCII**方案，通过不同的 code page 来适配不同语言的字符集。

但这些只是开胃菜。汉字、日文、韩文——成千上万个字符，一个字节（0-255）远远不够。于是各国又各搞各的多字节编码：日本用 Shift-JIS，简体中文用 GBK，繁体中文用 Big5。编码不一样，文件互相交换就是灾难。

**UTF-8 把这个问题一次性解决了**。它能编码全世界的所有字符，而且兼容 ASCII——也就是说纯英文的 UTF-8 文件跟 ASCII 文件完全一样。

现在绝大多数系统和工具都默认用 UTF-8。

### 餐巾纸上的设计

UTF-8 是谁发明的？**Ken Thompson 和 Rob Pike**。

先说这两个人是谁——Thompson 是 Unix 的创造者之一（对，就是那个 Unix），Pike 后来跟 Thompson 一起设计了 Go 语言。两个人都来自贝尔实验室。

1992 年 9 月的一个晚上，俩人在新泽西一家小餐馆吃饭。当时他们正在做 Plan 9 操作系统（一个比 Unix 还超前的项目），需要一种更好的文本编码方案。Thompson 顺手在餐巾纸上画了现在大家熟知的 UTF-8 编码规则：

```text
0xxxxxxx                         单字节
110xxxxx 10xxxxxx                双字节
1110xxxx 10xxxxxx 10xxxxxx       三字节
11110xxx 10xxxxxx 10xxxxxx 10xxxxxx  四字节
```

当天晚上 Thompson 就把编码和解码的代码写出来了，Pike 改完了 C 库和图形库。**三天后**，整个 Plan 9 操作系统完全切换到了 UTF-8——这是世界上第一个全面使用 UTF-8 的系统。下一个周一，X/Open 委员会投票采纳了这个方案。

一段餐巾纸上的涂鸦，变成了今天互联网上最通用的编码。

## UTF-8 是怎么做到的

UTF-8 最巧妙的地方：**它能用 1 个字节表示英文，2-4 个字节表示其他字符，而且解码器永远知道自己读到的是哪种**。

先看个直观的例子。打开终端，对比一个英文字母和一个汉字在 UTF-8 里分别长什么样：

```zsh
echo -n A | xxd -b    # -n 让 echo 不加换行符
echo -n 中 | xxd -b
```

> **注意**：这里用了 `echo -n`，输出不带末尾换行。如果没加 `-n`，末尾会多一个 `0a`（换行符）的字节，跟编码本身无关，容易干扰观察。

我们会看到：

```text
# A 的二进制（1 字节）
01000001

# "中"的二进制（3 字节）
11100100 10111000 10101101
```

规则是这样的：

| 字节范围 | 编码形式 | 能表示的范围 |
|----------|----------|-------------|
| 0xxxxxxx | 单字节（兼容 ASCII） | U+0000 ~ U+007F |
| 110xxxxx 10xxxxxx | 双字节 | U+0080 ~ U+07FF |
| 1110xxxx 10xxxxxx 10xxxxxx | 三字节 | U+0800 ~ U+FFFF（中文在这里） |
| 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx | 四字节 | U+10000 ~ U+10FFFF |

关键看开头的比特模式：

- 如果字节以 `0` 开头 → 单个 ASCII 字符，读到 `xxxxxxx` 7 位就是字符编号
- 如果字节以 `110` 开头 → 这个字符占 2 字节，后面还有一个以 `10` 开头的"后续字节"
- 如果以 `1110` 开头 → 占 3 字节，后面跟两个 `10xxxxxx`
- 如果以 `10` 开头 → 不是新字符，而是某个多字节字符的"后续字节"

这个设计的妙处：

1. **自同步**——从文件中间任意位置开始读，最多跳过 3 个字节就能找到下一个字符的真正开头。不会像 GBK 那样跳错一步导致后面全乱。
2. **不混淆**——`10xxxxxx` 的模式永远不会跟字符开头字节的 `0`、`110`、`1110` 搞混。
3. **兼容 ASCII**——所有合法的 ASCII 文件同时也是合法的 UTF-8 文件。

用"中"字验证一下上面的公式：

```text
中 → Unicode 码点 U+4E2D，二进制 0100 1110 0010 1101（15 位）
→ 需要用三字节格式：1110xxxx 10xxxxxx 10xxxxxx
→ 把 15 位填进去：
      1110 0100   1011 1000   1010 1101
          0100     111000      101101
→ 十六进制：E4 B8 AD
```

```zsh
echo -n 中 | xxd
# 输出：00000000: e4b8 ad
```

跟公式算出来的一样。那些高位比特不是浪费，是精确的标记——告诉解码器"这个字符从哪里开始、到哪里结束"。

## 查看当前系统编码

```zsh
locale
```

```text
LANG="zh_CN.UTF-8"
LC_CTYPE="UTF-8"
LC_ALL=
```

> 具体输出因人而异，重点是找 `UTF-8`。`LANG` 和 `LC_CTYPE` 里有 `UTF-8`，就说明终端默认用 UTF-8。如果全是空或者只有 `C`，那终端用的是最基础的 ASCII。

查看文件的实际编码：

```zsh
file -I 文件名
```

```
文件名: text/plain; charset=utf-8
```

## 终端编码 ≠ 文件编码

搞清这个问题，90% 的乱码原因就明白了。

终端和文件各有各的编码：

- **终端编码**（由 `locale` 决定）——终端用什么编码来解释收到的字节流
- **文件编码**（用 `file -I` 查看）——文件本身是用什么编码存的

当我们 `cat` 一个文件时：

1. `cat` 把文件的字节原封不动地吐给终端
2. 终端用自己的编码去解释这些字节
3. 两边编码一致 → 显示正常
4. 两边编码不一致 → 乱码

所以看到乱码时的排查思路很简单：**终端和文件，谁的编码设错了？**
先查 `locale`，再查 `file -I`，然后决定是转文件编码还是调整终端设置。

## 常见乱码场景

### 场景 1：文件是 GBK，终端是 UTF-8

```zsh
cat old_gbk_file.txt
```

显示一堆乱码。

处理方法：

```zsh
iconv -f GBK -t UTF-8 old_gbk_file.txt > new_utf8_file.txt
```

`iconv` 是编码转换工具，`-f` 是原编码，`-t` 是目标编码。

### 场景 2：文件是 UTF-8，cat 正常，less 乱码

```zsh
less 文件.txt
```

`less` 默认可能没设对编码。退出来后设一下再打开：

```zsh
export LESSCHARSET=utf-8
less 文件.txt
```

也可以直接在 less 里按 `-` 然后输入 `r` 回车，开启原始显示模式，临时绕过编码问题。

### 场景 3：文件名乱码

```zsh
ls
```

看到 `?????.txt` 或者 `\xE5\x9B\xBE.txt`。

用 `convmv` 转码文件名（先装 `brew install convmv`）：

```zsh
convmv -f GBK -t UTF-8 --notest *
```

### 场景 4：vim 打开文件乱码

Vim 有三种跟编码相关的设置：

- `encoding`（`enc`）——Vim 内部用什么编码处理文本
- `fileencoding`（`fenc`）——文件保存时用什么编码
- `fileencodings`（`fencs`）——打开文件时依次尝试哪些编码

现代 Vim 通常自动识别编码，偶尔会猜错：

```
# 打开文件后发现乱码
:e ++enc=gbk        ← 用 GBK 编码重新载入

# 正常了，然后保存为 UTF-8
:set fenc=utf-8
:w
```

在 vim 里转编码的好处是不需要离开编辑器。

## 文件头（BOM）

有些编辑器会在 UTF-8 文件开头加三个特殊字节（`EF BB BF`），叫 **BOM（Byte Order Mark）**。

大多数时候没事，但偶尔会惹麻烦——比如 Shell 脚本加了 BOM 后，第一行的 `#!/bin/zsh` 就识别不了了。

```zsh
# 检查有没有 BOM
xxd script.sh | head -1

# 或者用 od
od -A x -t x1z -v script.sh | head -1

# 去掉 BOM（macOS sed 需要 -i ''，Linux 用 -i）
sed -i '' '1s/^\xEF\xBB\xBF//' script.sh
```

## macOS 上的编码陷阱：NFC 与 NFD

这个细节让不少 macOS 用户在跟 Linux 传文件时掉过坑。

Unicode 里有些字符可以用不同方式表示。比如带重音的 `é`：

- **NFC**（预组合）：`é` 作为一个整体，码点 `U+00E9`，UTF-8 编码是 `c3 a9`
- **NFD**（分解）：`e`（`U+0065`）+ 重音符（`U+0301`），UTF-8 编码是 `65 cc 81`——两个码点

两种写法显示的字符一模一样，但字节完全不同：

```zsh
# 预组合 é（NFC）
printf '\xc3\xa9' | xxd
```

```
00000000: c3a9
```

```zsh
# 分解后的 é（NFD）
printf 'e\xcc\x81' | xxd
```

```
00000000: 65cc 81
```

注意 `xxd` 的 ASCII 列——非 ASCII 字节会显示成 `.`。NFC 的 `c3 a9` 是**两个点**，NFD 的 `e cc 81` 是 **`e` 后面跟两个点**。

**macOS 的文件系统默认用 NFD** 存储文件名，大部分 Linux 系统用 NFC。

所以有些文件拷到 Linux 服务器后，看着名字一样，脚本却怎么也找不到——字节不同，系统认为是两个不同的文件。

```zsh
# macOS 上的文件名是 NFD，Linux 上的是 NFC
# 它们在 xxd 里看起来是这样：
# macOS: 6361 6665 cc81 2e74 7874    cafe.txt（e + 两个点）
# Linux: 6361 66c3 a92e 7478 74     caf..txt（两个点）
#                ↑                    ↑
#          同一个字母 'é'，不同字节
```

怎么检查当前文件名的实际字节：

```zsh
ls -b           # 用转义序列显示不可见字符
```

装 `convmv` 可以批量转换：

```zsh
brew install convmv
convmv -r -f utf-8 -t utf-8 --nfc /path/to/dir --notest
```

日常影响不大——macOS 和 Linux 通常都能正常显示。但写脚本遍历文件名、或在 Git 里看到文件"已修改"但内容没变时，测一下 NFC/NFD 很可能就是原因。

## 动手试试

```zsh
# 查看当前终端编码
locale | grep LANG

# 查看一个文件的实际编码
file -I ~/.zshrc

# 创建一个带中文的 UTF-8 文件
echo "你好 世界" > hello.txt
cat hello.txt
# 输出正常，因为终端和文件都是 UTF-8

# 故意用错的编码读——假装它是 GBK
cat hello.txt | iconv -f GBK -t UTF-8
# 编码不匹配，输出的是乱码

# 反过来：把文件从 UTF-8 转成 GBK，再用 cat 看
iconv -f UTF-8 -t GBK hello.txt -o hello-gbk.txt
cat hello-gbk.txt
# 终端是 UTF-8，文件是 GBK——输出乱码

# 用正确编码查看 GBK 文件
cat hello-gbk.txt | iconv -f GBK -t UTF-8
# 选对了编码就正常了

# 再看二进制区别——同一个字在两个编码里完全不同
xxd hello.txt | head -3
xxd hello-gbk.txt | head -3
```

---

## 小结

- **UTF-8** 是现在的通用标准，绝大多数情况用它就对了
- 看到乱码先用 `file -I` 查看文件实际编码
- `iconv -f 原编码 -t UTF-8` 把文件转成 UTF-8
- 自己新建的文件都存 UTF-8，能省掉 90% 的编码问题
